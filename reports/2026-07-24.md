### 1. Pushary · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/pushary) | [Web](https://www.producthunt.com/r/FVVAIY5OGI5VVM)

**定位**：手机锁屏上的 AI 代理审批中枢。终端里的 Claude Code / Codex /
Cursor / Gemini CLI 遇到需要人类点头的操作时，通知直接推到手机锁屏，一键
放行，agent 继续跑；配对靠扫码，不用往终端粘 API key，安全 read 类操作
可按工具做策略自动放行，所有决策留审计日志。

**差异点**：这是一个非常"贴身"的 agent-in-the-loop 基础设施位。同类
思路的产品要么走 Slack bot（延迟大、要求打开电脑）、要么做 Web
dashboard（要开一个 tab 盯着）。Pushary 的杀手锏是把审批从桌面工作流里
剥出来，走原生手机推送 + 锁屏交互，让"人不在电脑前"也能推进 agent。
"审批策略 + 审计"这套企业化配置，暗示他们瞄准 agent 规模化后
compliance 的真实痛点。

**技术判断**：不是套壳。要做锁屏一键审批意味着他们实现了原生 iOS /
Android app（今日就有）、要跑一套 push 中继服务把终端事件转发到手机、要
在 CLI 侧写多个 agent 的适配 shim（Claude Code / Codex / Cursor / Gemini
CLI / Hermes / Claude Cowork 都点名支持），还要维护 per-tool policy 引擎和
审计日志存储。工程量不小，pairing 走 QR code 而非 key 粘贴说明他们
认真处理了 secret 分发。

**信号价值**：agent-in-the-loop 正在从"每次都问 y/n"演化成"分级信任 +
异步审批"。这是 agent 走向 unattended long-running 场景的必经路径。
对做 AI agent 工具链的人而言，这块正在从"每个 agent 自己实现"抽象出
成一个横切基础设施——类似当年 push notification 之于移动 app。值得追。

### 2. Fluree AI · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/fluree) | [Web](https://www.producthunt.com/r/Y6SGXQZUGTMKAT)

**定位**：给所有 AI agent 一份"可验证的公司上下文"。用结构化数据层直
查企业数据，返回带引用的答案，权限逐请求校验，直接对接 MCP-ready 的
agent / dashboard / app。定位是 RAG 的替代方案，用图/规则/权限做
grounding，而不是靠 vector 搜索去猜。

**差异点**：和 vector-RAG 的差异是本质的——RAG 拼上下文碎片、依赖
LLM 融合，容易幻觉；Fluree 把"上下文层"变成一个带权限、带引用、可
查询的数据平面。同类里主要竞品是 Cognee、Datastrato、Weaviate 的
KG 方案，以及各家做 semantic layer + MCP 的团队（Cube、Fivetran 的
新 agent 层）。Fluree 有旧账（几年前的 blockchain-native RDF DB 时代），
这次 pivot 到 AI trust context 是典型的"知识图 + provenance"卡位
agentic 时代的姿态。

**技术判断**：核心资产在数据层——不可变账本 + 时序 RDF 结合权限模型，
本来就适合"每次请求带审计"这类需求。MCP 对接现在几乎是"上桌门票"。
挑战在于让企业愿意把结构化数据装进他们的 layer，这是销售问题不是技术
问题。

**信号价值**：反 RAG 或者说"post-RAG"叙事在 2026 年上半年明显加速——
把幻觉治在数据层，而不是靠 prompt / rerank / eval 事后打补丁。做 agent
的团队应该开始认真评估"provenance-first"这条线，不管是选现成的 KG
产品还是自己在业务数据上做 semantic layer。

### 3. HarnessRouter · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/epsilla) | [Web](https://www.producthunt.com/r/U5TRDBVG3MM4NB)

**定位**：一个 API 打通"世界上最好的 AI agent 后端"——sandbox、
orchestration、retry、成本控制这堆脏活它替你干，你输入需求，输出成品
（代码 / 文件 / 视频 / 游戏）。定位类似 OpenRouter 之于 LLM，但抽象
层次更高：路由的不是 model call，而是 agent capability。

**差异点**：现有 OpenRouter / Portkey / LiteLLM 路由的是"给我一次
completion"；Fal / Replicate 路由的是"给我一次单模型任务"。
HarnessRouter 想路由的是"给我一份完成的工作"——把 planning + tool
use + retry + sandbox 都封在服务端。竞品是各家 agent 平台自己
（Devin API、Manus、E2B + 自研 orchestrator）。风险在于抽象层选得
太高，客户对"最终交付物"的质量分布会有很强偏好，通用 router 未必
比垂直 agent 更好用。

**技术判断**：真做起来需要沙箱池（isolation + 冷启动优化）、结果验证、
成本熔断、失败重试 + partial credit 计价。挂"Epsilla"这个背景（原本
做 vector DB 的）——他们从检索层往 agent 层拉伸，路径合理。

**信号价值**：agent 世界正在长出"router"这个层——先是 model router，
再是 agent capability router，最终可能是"给我做完这件事"的
end-goal router。这个 stack 里谁能吃到通用抽象位，谁就吃到未来的
AWS 位。但过早通用化通常死于"什么都能做，什么都不好用"，值得放
watchlist 看客户实际留存。

### 4. OpenWorker · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/openworker) | [Web](https://www.producthunt.com/r/MR4WFZE7PG6HBL)

**定位**：跑在你自己电脑上的 local-first desktop agent，操作你日常的
本地工具，做完给你交付；关键动作前会 check-in。免费、开源、BYO model。

**差异点**：桌面 agent 这条线上，Manus / Devin / Cove 是云端；Anthropic
Computer Use、OpenAI Operator 云侧执行；Rabbit / Adept 之前的路线部分死
在延迟和不确定性上。OpenWorker 走的是"本地 + 开源 + BYO"三件套——这
正对上了 privacy-first、审计合规、以及"我已经付了 API key 不想再付一层
SaaS"这三类需求。竞品是 Simular、Skyvern 这类偏本地或半本地的开源
方案。开源本身是最大差异——审计代码、二次开发、部署到内网都成立。

**技术判断**：本地跑桌面 agent，最难的是"跨应用可靠操作"——OCR /
accessibility API / 快捷键映射的鲁棒性，以及断点续跑。"check in before
anything important"说明他们把 human-in-the-loop 放在了核心 primitive
里，而不是事后加。BYO model 意味着他们在 planning / tool-call 上做
了 vendor-agnostic 抽象，这是好的工程判断。

**信号价值**：local-first agent 这条线过去半年在开源社区悄悄升温
（配合 Pushary 的手机审批，可以想象整个"本地 agent + 远程审批"链
路开始成型）。做 agent 的团队，如果你的产品有云端锁死的部署方式，
面对 local-first 开源竞品会越来越难卖。这个赛道值得跟。

### 5. The new Firecrawl /search · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/extract-by-firecrawl) | [Web](https://www.producthunt.com/r/H7JTV6NB7D5IKG)

**定位**：给 AI agent 用的搜索 API，训练了自己的模型专门从每个搜索
结果里提取"最能回答查询"的段落，跳过整页解析。号称在 SimpleQA 上
以 10x 更少 token 达到 94.7%，超过所有其他供应商。

**差异点**：这是一次功能升级而不是新产品，但方向很有代表性。
Perplexity / Tavily / Exa / Serper / Brave Search API 都在这块卷。差异
点是他们不再是"网页返回 → 交给 LLM 自己抽"，而是自己训了一个
段落级 relevance model 做前置压缩。这个思路和 Cohere Rerank 类似，
但落地在 web search 这个 agent 首选 grounding 源上，价值更实际。

**技术判断**：训自己的 excerpt selection 模型是真工程动作——数据管
线、evals、benchmark 都要落。SimpleQA 94.7% 这个数字需要独立验证，
但至少有 concrete benchmark 数字（比大多数发 PH 的"AI search"产品
诚实）。10x token 节省对下游 agent 成本影响不小。

**信号价值**：AI agent 时代 web search 正在从"搜索 API"变成
"grounding-optimized API"。这不再是给人看的搜索结果排序问题，而是
"如何用最少的 token 把最相关的证据交给 LLM"的问题。做 agent 后端
的团队应该开始按 token/answer accuracy 曲线来选搜索供应商，而不是
按传统搜索质量指标。
