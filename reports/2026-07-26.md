### 1. Openbase · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/openbase-2) | [Web](https://www.producthunt.com/r/U7DUSA6V3LZT5Q)

**定位**：用语音从手机上派任务给一队 AI 编程 agent，也能在 agent
干到一半时插话改方向，改动出 PR 之后语音批准。跨 provider，桌面端
同步会话，回到电脑前能接着干。

**差异点**：这和昨天的 Heard 是同一趋势的两个不同工种。Heard 解决
"眼睛不在电脑前时 agent 在说什么"（听），Openbase 解决"手不在键盘
上时怎么改 agent 在做什么"（说 + 决策）。都是把 agent 的 UI 从
终端里搬出来。区别是 Heard 走被动 + 开源 + 只做 Mac；Openbase 走
主动控制 + 手机为主 + 跨 provider。真正的竞品是 Warp / Cursor 的
mobile 影子，但那两家目前是"在手机上看 agent 状态"，没到"在手机
上导航 agent 的执行"这一步。

**技术判断**：几个必须做对的工程点：手机语音到桌面 agent 的实时链
（延迟不能高于人说话的节奏，否则打断体验塌）、agent 状态的
canonical model（不同 provider CLI 输出格式不同，怎么归一化才能
"跨 provider" 而不是每家写一版）、桌面同步走什么协议才能既支持
"回到电脑接着干" 又不把敏感 diff 走云。做成 SaaS 说明他们选择托管
中继而不是 P2P——这是有意的商业选择，但也是最容易踩雷的一段。

**信号价值**：如果昨天 Heard 是信号，今天 Openbase 就是趋势确认。
**agent-in-the-loop 的 I/O 层正在按感官通道分裂重组**：听 (Heard) /
说 (Openbase) / 手机推送审批 (上周 Pushary)——三个通道都有人在做，
而且都不是简单的通知包装，而是真的把"人类不在座位上"这段体验拆开
在做产品。做 AI 编程工具的团队今年该问自己的问题不再是"要不要接
Cursor"，而是"我这个产品在'眼睛/耳朵/手/桌面/手机'这个矩阵里占
哪一格？"

### 2. Athena by Shoplazza · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/athena-by-shoplazza) | [Web](https://www.producthunt.com/r/BFVWD7733PP65I)

**定位**：Shopify-style 建店里的 "vertical orchestrator agent"。
不是聊天式辅助——一句"帮我开店"下去，页面、产品、本地化文案、批量
上货、折扣、发货、广告投放整条链自动跑；支付/物流/履约/会员都长在
同一个平台里，agent 只是壳，底下是 Shoplazza 自家的 e-commerce
栈。

**差异点**：和 Shopify Sidekick / Magic 的关键不同：Sidekick 是
"辅助建站"，Athena 是"orchestrator"——差别在 agent 能不能真的去
launch ad campaigns、配 shipping、创 discount，而不只是给建议。
这一步能做，是因为 Shoplazza 把履约/支付/广告都自己做了，agent
调用的是自家 API 不是拼积木。这也是为什么 Shopify 短期未必能抄——
他们的商家想要的深度集成，跟自研全栈的 Athena 不是一回事。

**技术判断**：真正的护城河不在 LLM，而在 **"电商域动作 API 的
完备度 + 权限模型"**。orchestrator agent 的失败模式一般是权限暴
露 / 不可回滚——388v/126c 里那么多评论多半是围绕"下单 / 投放广告
这种动作 agent 能不能自主执行"。看不到的部分：动作执行链的
transaction 边界怎么划？投错广告能不能撤？跨 workflow 的状态
一致性怎么保？这些回答质量决定它是 demo 还是真业务工具。

**信号价值**：过去一年 SaaS 里最会做 "vertical agent" 的赢家一
直没定——GTM 域的 Clay、支持域的 Fin、都还在跑马圈地。Athena
是电商域第一个把 orchestrator 这个词打出来的头部竞品。信号：
2026 H2 的一批 vertical agent，比起"通用 agent + 集成"，更可能
是"自研全栈 + agent 作为唯一入口"这种反向路径。做 horizontal
agent 工具的团队要注意：垂直方深度集成后，你的 API integration
故事会越来越难卖给这些"agent = 整个产品"的公司。

### 3. Braidkeep · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/braidkeep) | [Web](https://www.producthunt.com/r/DKK6HUVKHZFVOA)

**定位**：并行跑多个 AI coding agent 的时候，用 git 的 merge-tree
（只读，不动 working tree）预测哪些分支会冲突、按"无冲突批次先合，
纠缠的最后合"计算安全的合并顺序，附带 per-agent 文件所有权强制。
单二进制、Apache-2.0。**"预测可合性，不预测正确性"**——作者自己
划的边界。

**差异点**：这是我今天最想推的产品，虽然只有 18 票。目前
multi-agent orchestration 层（Claude Code 的 parallel subagents、
Cursor Composer、Devin 的 fleet 模式）都在拼"并发跑更多 agent"，
但**合并的问题一直被推给最后**——你 5 个 agent 都完成了，一个个
合，前 4 个改动全被最后一个 revert 掉，浪费 4 份 tokens。Braidkeep
明确锁定的是这一段。同类里 Graphite 的 stack 是给人用的、
git-town 是给人用的，专门给"多 agent 并发"设计的合并层，我印象里
这是第一个。

**技术判断**：技术选型很克制——直接用 `git merge-tree` 而不是自
己重实现 diff3，这个是对的（正确性比性能重要）。真正难的是
"per-agent file ownership" 这一层：如何在 agent 开始工作前就知道
它会碰哪些文件？两种做法——事后从 diff 反推 vs 事前从 task
description 推断，前者延迟高但准，后者快但需要 agent 配合声明
scope。产品文案没说清用哪种，值得追一追。开源单二进制的形态很
适合被 embed 到 orchestrator 里，可能是有意的分工。

**信号价值**：这是 **"AI-authored code 的基础设施空档"** 里出现
的第一个正经工具。过去 12 个月大家都在做"跑更多 agent"，但
run-many 之后的 verify / merge / rollback 这三段一直是空的。
Braidkeep 抢了 merge 位。做 orchestrator 的团队应该认真看：与其
自己写合并调度，不如接一个 Apache-2.0 的模块，把精力留给上层。
另一个隐含信号：**"AI 编程栈里，非 LLM 的传统 SE 工程反而是新
护城河"**——git、merge-tree、DAG、job scheduling，这些老工具在
新场景下有第二次机会。

### 4. Verlox · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/verlox) | [Web](https://www.producthunt.com/r/QK2V3BE2KXSDXQ)

**定位**：Windows 上的 "AI 终端"，规则是"永不信任，总要验证"。
AI 出计划 → 人审批 → 才执行。每条命令变成一个带自然语言摘要的
block；删除操作走 Recovery Vault，可以 undo；所有动作落 timeline。

**差异点**：和 Warp / Wave / Fig 那批"AI-augmented terminal"最大
区别在**默认模式**。Warp 的 agent 模式是"执行为主，审批为例外"；
Verlox 反过来——审批为默认，执行为例外，加上真正的 undo 层。
Windows-first 也是罕见选择（Warp 长期只 Mac，Wave 也是 Mac 优先），
说明这拨"要求安全"的用户在 Windows 里很集中——很可能是企业 IT
和金融行业的 dev。

**技术判断**：Recovery Vault 是关键。"undo" 在 shell 语境里从来
不是免费的——`rm` 走 vault，`git reset` 是不是要拦？跨 process
的副作用（网络请求发出去了、DB migration 跑完了）能不能 undo？
文案说的是"deletes 走 Recovery Vault"，说明 undo 的语义可能是
"文件级 undo"，不是"任意副作用 undo"。这个边界选得对——不承诺
undo 网络调用是诚实的。但要看 timeline / block 系统的实现深度
——如果只是把 shell 命令包一层 UI，一年后没竞争力；如果 block
是一个可组合的执行单元（能 replay、能 export 成脚本），那就有
护城河。

**信号价值**：跟 Braidkeep 是同一件事的两个侧面——**AI 生成的
副作用需要在执行层加保护**，一个在 merge 边界（Braidkeep），一个
在 shell 边界（Verlox）。加上 Hyper 那种"hard cost caps"，可以
看到一个更大的方向：**agent safety 从 prompt/model 层下沉到
runtime 层**。做 agent 产品的团队今年要开始想 runtime safety
的 SLA 怎么定，而不是继续在 system prompt 里加"请不要 rm -rf"。

### 5. CodexBar Lite · ⭐⭐⭐
[PH](https://www.producthunt.com/products/codexbar-lite) | [Web](https://www.producthunt.com/r/IWZXMU2ZWFQXDM)

**定位**：macOS menu bar 里的 OpenAI Codex 用量监控。**不要 API
key，不要浏览器 cookie，不要 Keychain 权限，不要第三方账号**——
直接复用你本地已有的 Codex CLI 会话文件。开源。

**差异点**：市面上追 AI 用量的工具（ccusage / 一堆 Claude Code
tracker）多数走 API key 或跑代理拦请求。CodexBar 的选择是"读
CLI 已经存好的会话"——这是一个小但正确的工程决策：**session
文件本来就在磁盘上，你已经登录过了，为什么要再走一次 auth？**
少一层集成、少一层权限、少一层攻击面。

**技术判断**：本质是"依赖 CLI 的 on-disk state 文件当稳定
API"。这条路的风险是 OpenAI 改 session 文件格式就会破——但
Codex CLI 是官方产品，格式相对稳定，而且开源可以快速跟。相比
写一个 MITM 代理去拦 API 请求，这个方案对用户的干扰最小，也最
符合"privacy-first"的定位。

**信号价值**：这是当天最小的一个，但它体现的模式在放大——
**"AI 工具的周边工具"正在形成子生态**。上周 Heard 是"给 Codex/
Claude Code 加语音"，今天 CodexBar 是"给 Codex 加用量看板"，
再加上 ccusage 系列。**围绕 Claude Code / Codex 这两个 CLI 的
第三方生态开始成气候了**——就像早年 vim/emacs 有插件市场一样。
做 CLI-first agent 产品的公司要开始想：我给周边工具留了什么
hook（config 文件位置、日志格式、session 结构）？留得好，别人
给你造生态；留得随意，别人只能反向工程。
