### 1. The GTM Co-Founder · ⭐⭐⭐⭐

**定位**：把"GTM 教练"打包成一组 open-source Claude/agent skills，
针对技术型 founder：一次访谈问清产品与市场，之后按阶段给出 who /
positioning / first 50 users / launch / pricing 的可执行下一步。

**差异点**：市面上的"AI 商业顾问"绝大多数是 ChatGPT 上的一段 system
prompt 或独立的 SaaS 咨询产品。它选择的形态是**"skills"作为可分发
artifact**——不是 chatbot、不是 SaaS，是一份可以 fork 的仓库，跑在
用户自己的 agent runtime 里。类比 dbt 之于分析、prompt library 之于
2023 年的模板分享。

**技术判断**：无自研模型、无 backend。价值全部在**内容质量 + 结构化
的 skills 分层**（每一步都是可组合的最小单元，可以被 agent 按需
load）。Adam Frankl / Jakub Czakon 的 GTM 方法论提供内容护城河，
形式护城河来自"用户的 agent 就是执行器"——不用做产品化 UI 就能
serve 每个用户。

**信号价值**：**"skills as first-class artifact"这个抽象昨天开始在
榜单前列出现。**过去半年榜单上"agent + 领域知识"都以 chatbot 形态
出现（Ellie for legal / Harvey style），今天两个头部产品选择了完全
不同的形态。如果这条路走通，会出现"skills 生态"——skills 商店、
skills 版本化、skills 安全评估——这本身是 dev tool 层的新范畴。
值得持续跟踪。

**关注度**：⭐4/5 — 内容驱动的项目通常长尾能力弱，但形态本身是
新的，值得作为"skills 分发"这条线的锚点样本。

### 2. Hexis · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/bevel-4) · 182v / 8c

**定位**：企业级 "AI skills / tools / context" 中央仓储。基于 Git
（PR、review、版本），加一层 UX 让非工程人员也能提交/使用，加
访问控制。任何支持 MCP 的 agent 都能消费。

**差异点**：目前 agent 生态最脏的一环是 "context / tools / prompt"
的治理——每个人的 Cursor / Claude / VS Code 里都塞着一堆 MCP server
和 prompt fragment，个人层面就已经难以管理，公司层面几乎无解。
现有方案大致三类：(a) MCP registry / marketplace，只解决发现；
(b) LangChain hub / promptfoo 之类，工程师内部工具，非技术不用；
(c) 各家 IDE 自带的 rules 文件，锁定单 vendor。**Hexis 的锐度在于
"把 Git 当基础设施"**——绕开自建版本层、绕开自建权限层，专注做
"人+agent 都能用"的 UX 层和 MCP 消费面。

**技术判断**：核心工程量在 (1) 把 Git 的 branch/PR 语义暴露成非
工程可理解的操作，(2) MCP server 作为消费面，把 skills / tools
按 policy 动态提供给不同 agent。**架构上是"Git as data plane + MCP
as data path"**——如果做得好，就是 agent 生态的"包管理器 + 权限
中心"合体。

**信号价值**：与 Top 1 The GTM Co-Founder **同一天出现在榜前**不是
巧合。当"skills 作为产品形态"开始铺开，**"skills 的分发 / 治理 /
版本"就是必然的下一步**——The GTM Co-Founder 是 skills 生产者，
Hexis 是 skills 分发/治理层。这一对组合基本预告了下半年 AI infra
的一个新层次。对做 AI agent / dev tool 的方向，这是**必读样本**。

**关注度**：⭐5/5 — 罕见的"卡位精准 + 时机对 + 架构选择正确"的
组合。跟踪 3–6 个月看是否能吃到企业订单。

### 3. Toolport · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/conduit-12) | [Website](https://www.producthunt.com/r/5CMO6NALORXKZD) · 149v / 4c

**定位**：本地 MCP gateway。所有 MCP server 只在这里配置一次，
所有 agent（Claude / Cursor / VS Code / Codex 等 33 家）共享。
不再把工具定义全量灌 context，而是暴露"元工具"让 agent 按需
search，token 用量下降到原来的 9%（benchmark 声称 91% 节省，
同任务成功率）。secrets 存 OS keychain，破坏性调用有 approval
gate，rug-pull / tool poisoning 会告警。

**差异点**：MCP 目前的痛点非常具体——(1) 每个 client 都要重复
配一遍，(2) 工具定义会把 context 撑爆（几十个 MCP server 光
schema 就上万 token），(3) 供应链风险几乎无人管。**Toolport
不是发明新协议，而是做"聚合 + 优化 + 安全"三合一 layer**。类比
kube-proxy 之于容器网络——不改变协议，改变运行时。

**技术判断**：核心工程量：(a) meta-tool 的检索层——需要在无
模型微调的情况下让工具搜索准确率不掉；(b) 供应链检测——tool
poisoning / rug-pull 检测意味着他们在跟踪 MCP server 的行为
变化；(c) 33 家 client 的适配矩阵。**"91% token 节省 + 同任务
成功率" 如果 benchmark 可复现，是**目前 MCP 生态最重要的性能
数据点。

**信号价值**：与 Hexis 组合起来看，**MCP 从"协议规范"跨越到
"产品化 runtime"这一步正在完成**。8 月 6 日的 Cloudflare OS
是"OS 层"的宣示，今天 Toolport 是"gateway 层"的落地。做 agent
产品的团队近期应该开始考虑：不要自己维护 MCP server 集合，走
第三方 gateway 更划算。

**关注度**：⭐5/5 — token 节省 benchmark 如果真实，这是压倒性
的采纳理由。是今天的**第二个必看**。

**关注度**：⭐3/5 — Demo 赛道竞争激烈且已被大玩家占位，但作为
