### 1. Prelint · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/prelint) | 564 votes / 127 comments (r=0.23)

**定位**：给 AI 写的代码做"产品一致性"审查——每个 PR 都会被拿去对齐
你的 ADR、文档和历史决策，抓的是"实现是对的但方向偏了"这种 human
reviewer 也容易放过的漂移，而不是语法或安全漏洞。

**差异点**：跟 CodeRabbit / Greptile / Cursor Bugbot 这批 AI code
reviewer 比，主张不再是"帮你抓 bug"，而是"抓产品意图上的偏差"。这在
"AI 出码速度 10x 但产品负责人还是 1x"的团队里是一个真实痛点——他们
自己给的数据是：在同时用多个 AI reviewer 的团队里，40% 的合入前
修复来自 Prelint（其他 reviewer 抓不到）。把"知识源"（ADR + 决策记录）
和 diff 放到同一个 judge 里是关键工程决定。

**技术判断**：核心是检索——如何在几十份 ADR / 几百条历史决策里为一个
PR 精准挑出相关约束，是决定信噪比的分水岭。判 diff 相对容易，但要
说清"这段实现违反了 2 个月前 ADR-017 里的决定"，需要文档结构化 +
高质量 retrieval + 有解释性的 judge，都是有实打实工程量的。tagline
"AI writes at 10x speed" 是明面上的对齐，说明团队目标客户就是已经在
用 Cursor / Claude Code 的团队，而不是从零教育市场。

**信号价值**：AI code review 从"抓 bug"细分成"抓意图偏离"是 2026 下
半年一个明确的分层信号。上一层（correctness）逐渐被上游模型自身吃掉，
下游只能往 organizational context 走。做 dev tools 的团队应该假设
"通用 code review"会被压平，垂直到 "组织记忆 / 团队决策 / 产品约束"
这一层才有增量价值。相邻的可以盯：Sourcegraph Cody Review、Graphite
Diamond、Aviator Reviewer。

### 2. /mission for Claude Code · ⭐⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/spine-2) | 305 votes / 35 comments (r=0.11)

**定位**：一个 Claude Code plugin，输入一个"outcome"（比如"实现 X
feature"），它会自动拆成 live graph，把 Claude Code 与 Codex worker
一起编排跑，跑完汇总结果再接着推进。BYOK via OpenRouter，可以接
Kimi / GLM。

**差异点**：跟 Task Monki（今日 #9）、CrewAI、AutoGen、LangGraph 比，
最大差异是"plugin 而不是独立 IDE / 独立 framework"——不改开发者工作
流，直接寄生在 Claude Code 里。对比其他"Claude Code + Codex 双跑"
方案（多数是 shell 脚本或者 tmux 编排），/mission 把它包成一个正儿
八经的 mission graph，是往产品化走。BYOK + 支持 Kimi / GLM 是另一个
差异点，很明显不想被单一模型厂锁死。

**技术判断**：难点在于"outcome → task graph"的分解质量，以及 worker
之间的结果合并——LangGraph 系产品在这上面挣扎两年了，谁能让
非工程用户也能画出可跑的 graph 是壁垒。做成 Claude Code plugin 是
聪明的分发策略：不需要用户切换环境。但也意味着上限被 Claude Code
的 plugin API 限制住，宿主更新可能会伤到自己。团队里有 Spine AI
（YC S23）的 CEO，履历上有对多 agent 编排的严肃投入。

**信号价值**：这是本季度里我看到的第一个"多 agent 编排作为编辑器
plugin"的产品化尝试。前两年多 agent 都是独立框架或独立 UI，用户
必须离开工作环境；这次把整套流程压到了 slash command 里，是分发
路径的重要变化。做 agent 产品的团队现在应该同时考虑两个交付形态：
独立 app 和 IDE / CLI plugin。后者获客成本远低但受宿主限制。

### 3. MemoryCustodian · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/memorycustodian) | 164 votes / 28 comments (r=0.17)

**定位**：给 Codex / Claude Code / Gemini 等编码 agent 一个"repo
原生"的持久记忆——决策、约束、被否掉的方案、项目上下文都以 markdown
存在 repo 里，跟代码同样被 review、被 version、可删除。加一个 manifest
决定每个任务加载哪些 memory，避免 prompt bloat。开源，local-first，
跨 agent。

**差异点**：跟 mem0、Zep、Cursor Memories、Claude Projects 这批
memory 产品比，最大差异是"存在 repo 里而不是我们云上"。前者的模式
需要你把项目上下文交给第三方 SaaS；MemoryCustodian 就是一堆
markdown + manifest，跟着 git 走。cross-agent 也是差异点——多数
memory 产品绑死单一 agent（Cursor Memories 只服务 Cursor），
MemoryCustodian 是格式协议而非托管服务。

**技术判断**：技术含量的重头在 manifest 设计——如何标记 memory 与
文件路径 / 任务类型 / 关键词的相关性，决定 relevant-only 检索能不能
真的压 prompt 大小。做成 markdown 也就意味着 memory 本身是 human-
readable / diffable / PR-reviewable，这是"记忆作为代码"的完整实现。
门槛不是模型能力而是格式约定与生态采用。

**信号价值**：coding agent 的记忆问题正从"每家自己搞一个 sidecar"
往"repo 原生 + 协议化"演进——跟 07-28 的 Lamoom（agent 跑在你的
Claude 里）、07-25 的一批 local-first 产品是同一条趋势线：**数据
主权正从 agent 厂手里被夺回到用户 repo 里**。这条线上做协议 / 标准
的产品有先发优势，因为一旦被多家 agent 消费方接入，就形成事实标准。
值得盯：AGENTS.md（GitHub 官方规范）、Cline 的 memory bank、
Continue 的 project memory。

### 4. Epilude · ⭐⭐⭐⭐
[PH](https://www.producthunt.com/products/epilude) | 118 votes / 14 comments (r=0.12)

**定位**：Mac 上的按键语音听写——按住一个键说话，松开就把润色好的
文本落到当前 app。会自动转写、加标点、清理口误、匹配语气，全程
on-device。

**差异点**：跟 Superwhisper、Wispr Flow、macOS 内建 dictation 比，
差异点有两个：(1) 全本地推理（Wispr Flow 是云端）；(2) "polish 到
匹配语气"这一步——多数 dictation 产品到"标点 + 段落"就停，Epilude
主动做重写。相对 Superwhisper，Epilude 的定位更偏"一键出终稿"而
非"高质量转写"。1 秒延迟是它主动喊出来的性能指标，说明团队意识到
这类产品的核心是感官延迟，不是转写准确率。

**技术判断**：本地跑一个足够好的语音模型 + 一个足够快的语气润色模型
是有硬工程量的——大概率是 whisper.cpp（或 MLX 版）+ 蒸馏过的小
LLM。1 秒端到端在 M 系列上是激进目标，能兑现的话 M4 Pro/Max
的市场价值会被这类产品放大。用户数据不出本机是明显卖点，也是
Wispr Flow 反复被质疑的点。

**信号价值**：本地推理产品在 2026 上半年从"技术演示"进入"合格
消费级"阶段，Epilude 是这一波中定位最纯粹的一个（没有云端 fallback、
没有账号系统）。做本地 AI 产品的团队值得学它的产品收敛：只做一件事、
延迟做到极致、明确拒绝云端功能。对比 07-28 的 Liminal（local-first
文档），local-first 已经从概念稳定成一类产品哲学。

### 5. JusTTY · ⭐⭐⭐
[PH](https://www.producthunt.com/products/justty) | 94 votes / 12 comments (r=0.13)

**定位**：一个用 Swift + libghostty 构建的 macOS 原生终端，明确不做
power user 那些花哨功能，只做日常够用的部分。

**差异点**：跟 Ghostty 本身（Mitchell Hashimoto 那个）、Warp、
iTerm2、Alacritty 比，JusTTY 是明确的"最小化 Ghostty 前端"——它把
libghostty（渲染 / VT 处理 / GPU）当依赖复用，只写 Swift 层的 UI
外壳。本质上是"用 Ghostty 的核当引擎，做一个更轻的 macOS 前端"。
这个思路很像早期的 WebKit / Blink 分叉——引擎归一，前端多样化。

**技术判断**：libghostty 作为独立库这一年才逐步稳定，第三方基于它
构建的第一批终端出现，是 Ghostty 从"应用"变成"平台"的信号。Swift +
libghostty 的组合意味着与 macOS 原生行为深度绑定（NSMenu、系统
文本服务），这是 Warp（Rust + custom UI）不占的位。产品定位主动收
缩到"简单"，是理性的——跟主线 Ghostty 拼功能没有意义。

**信号价值**：终端这个赛道在 AI agent 时代重新变有意思了——AI 会
把 CLI 变成主界面（Claude Code / Codex 都是 CLI-first），意味着
terminal 本身的 UX 会被重新定义。JusTTY 的出现说明 libghostty 的
生态开始形成，未来一年可能会看到更多"专门给 agent 用的终端"
（记忆 buffer、结构化输出、pane 编排给 tool call）出现。做 dev tools
的团队可以关注 terminal 作为"agent 载体"的方向。
